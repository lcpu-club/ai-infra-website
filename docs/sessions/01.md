## 1.1 · MLSys on GPU

### 从 latency 到 throughput

CPU 通常花费大量硬件资源优化少量线程的响应速度：复杂控制、乱序执行与大缓存都服务于较低的单线程延迟。GPU 则把更多资源用于大量相对简单的执行单元，通过同时保持大量可运行 warp 来隐藏访存与流水线延迟。

一个非常重要的实验是：**单个 GPU thread 甚至可能比 CPU 更慢**。只有把足够多的独立工作分配给大量 thread 与 block 后，GPU 的总体吞吐优势才会显现。

| 视角 | CPU | GPU |
| --- | --- | --- |
| 主要目标 | 单线程 latency | 总体 throughput |
| 并行规模 | 少量复杂核心 | 大量相对简单的执行单元 |
| 隐藏延迟 | Cache、乱序与预测 | 切换到其他可运行 warp |
| 合适工作 | 复杂控制、串行依赖 | 大规模、规则、数据并行 |

### SIMD、SIMT 与 SPMD

- **SPMD** 描述程序组织：许多执行实例运行同一个程序，但处理各自的数据。
- **SIMT** 是 CUDA 暴露的编程与执行模型：每个 thread 拥有自己的索引、寄存器状态和控制流视角。
- 硬件会把一组 thread 组织为 **warp**，共同取指和调度。
- 当一个 warp 内的 thread 选择不同分支时，硬件需要分批执行不同路径，这就是 branch divergence 的代价。

::: tip 一个持续有用的视角
先站在一个 thread 的局部世界里理解“我处理哪份数据”，再退后一步看硬件如何把许多 thread 打包成 warp、把许多 warp 和共享资源组织成 block。
:::

## 1.2 · CUDA Programming Model

### Thread → Block → Grid

- **Thread**：执行 kernel 的最小程序实例，通过自己的 index 选择数据。
- **Warp**：硬件实际共享控制与调度的一组 thread。
- **Block / CTA**：可共享 shared memory、进行同步，并被整体放置到一个 SM 上的协作范围。
- **Grid**：一次 kernel launch 创建的所有 block。不同 block 必须能够独立执行，以便同一程序扩展到不同规模的 GPU。

### 一个最小 Vector Add

```cpp
__global__ void vector_add(
    const float* x,
    const float* y,
    float* output,
    int n
) {
    int index = blockIdx.x * blockDim.x + threadIdx.x;
    if (index < n) {
        output[index] = x[index] + y[index];
    }
}

int threads = 256;
int blocks = (n + threads - 1) / threads;
vector_add<<<blocks, threads>>>(x, y, output, n);
```

这段代码虽小，却包含了 CUDA thread-level 编程最关键的组成：

1. Host 发起 kernel launch。
2. Grid 被拆成多个 block。
3. 每个 thread 根据 `blockIdx`、`blockDim` 和 `threadIdx` 计算全局索引。
4. 边界 thread 使用 guard，避免访问数组之外的数据。

### Block 不只是语法分组

一个 block 会消耗 thread slot、register 和 shared memory 等 SM 资源。因此，能够同时驻留在一个 SM 上的 block / warp 数量是有限的。这解释了为什么 block size、register pressure 和 shared-memory usage 会影响 occupancy，也解释了为什么 block 是 GPU 优化中反复出现的边界。

本节只建立直觉；具体的 coalescing、shared memory、bank conflict 与 tiling 将在 Session 02 展开。

## 1.3 · 从 Thread-Level 到 Tile-Level

比较同一个 vector add，可以清楚看到抽象层的变化。

::: code-group

```cpp [CUDA]
__global__ void add(
    const float* x,
    const float* y,
    float* out,
    int n
) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = x[i] + y[i];
}
```

```python [Triton]
@triton.jit
def add(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(axis=0)
    offsets = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offsets < n

    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)
    tl.store(out_ptr + offsets, x + y, mask=mask)
```

```python [TileLang · 示意]
@T.prim_func
def add(
    x: T.Tensor((n,), "float32"),
    y: T.Tensor((n,), "float32"),
    out: T.Tensor((n,), "float32"),
):
    with T.Kernel(T.ceildiv(n, BLOCK), threads=128) as bx:
        for tx in T.Parallel(BLOCK):
            i = bx * BLOCK + tx
            if i < n:
                out[i] = x[i] + y[i]
```

:::

CUDA 从单个 thread 出发，开发者显式描述 thread 如何映射到数据。Triton 从一个 program 所拥有的一组 offsets 出发；编译器负责把 tile 内的操作继续映射到硬件。TileLang 则进一步提供带有 memory scope、copy、GEMM 与 pipeline 语义的 primitive。

关键不只是“代码更短”，而是责任边界发生了变化：

| 决策 | CUDA | Triton / TileLang |
| --- | --- | --- |
| 单个 thread 的索引 | 用户显式编写 | 通常由 tile / program lowering |
| 数据 tile 的划分 | 用户通过 block 与索引表达 | 用户直接表达 |
| 边界处理 | thread guard | mask 或 DSL 控制流 |
| 数据移动与同步 | 用户显式控制 | 部分交给编译器，关键策略仍可暴露 |
| 高层语义 | 主要是通用指令 | 可包含 copy、GEMM、pipeline 等 primitive |

### 为什么 Tile 会反复出现？

GPU 优化经常围绕同一个问题展开：**怎样让一块数据被某个协作单元拥有，并在更近的 memory scope 中重复使用？**

GEMM 是最直观的例子。朴素实现反复从 global memory 读取输入；register tiling 让一个 thread 复用局部数据；shared-memory tiling 让整个 block 共同复用一块输入。后续的 Tensor Core layout、TMA 与 pipeline，仍然是在回答 tile 如何被表示、搬运、计算与同步。
