## Session 01 参考资料与内容建议

### Session 范围

- 1.1 MLSys on GPU：SIMD/SIMT、throughput vs latency
- 1.2 CUDA Programming Model：thread coordination & execution，包括 grid/block/thread、kernel launch、host/device、warp
- 1.3 Triton/TileLang：CTA-level programming，包括 program/block、tile abstraction、elementwise kernel

这份资料主要供 Session 准备者使用。建议不追求把 CUDA 或 DSL 面面俱到地介绍完，而是帮助听众形成几个能持续使用的心智模型：GPU 为什么选择高吞吐设计、SIMT 为什么表现为 thread/block/grid、tile abstraction 为什么自然地从数据复用和 GEMM 优化中出现，以及 DSL 在 CUDA 之上隐藏了什么、保留了什么。

## 建议的 Session 组织

Session 可以按“心智模型 -> 具体实现 -> 抽象提升”的顺序组织，但不必强行给所有内容贴上第一性原理标签。

### 1.1 MLSys on GPU

- 从 CPU vs GPU 的设计目标切入：CPU 优化单线程 latency，GPU 优化整体 throughput。
- 说明 GPU 把更多面积用于大量相对简单的计算单元，并通过大量可运行 warp 隐藏 latency。
- 用 `gpu_1thread` 比 CPU 更慢、而 multi-block GPU 快很多的 benchmark 建立直觉：GPU 不是“单个核心更快”，而是“并行度足够时吞吐更高”。
- 引出 SIMD/SIMT，但先避免陷入术语：可以从“每个 lane/thread 看到的是自己的程序和数据，硬件实际把一组 thread 放在同一个 warp 中执行”来解释。
- 主要资料：LCPU Part 0、15-779 slides 1-4、CUDA Programming Guide Part 1.2。

### 1.2 CUDA Programming Model

- 先从一个 thread/lane 的局部视角讲 SPMD：每个 thread 执行相同 kernel，通过不同 index 处理不同数据。
- 再引入 warp，说明共享控制流带来的面积和吞吐优势，以及 branch divergence 的代价。
- 然后解释 thread/block/grid 不是单纯的命名层次：block 是可以共享 shared memory、进行同步并被整体调度到 SM 的协作单元；block 之间必须独立，grid 提供足够多 block 让硬件扩展到不同规模 GPU。
- 用一个完整但最小的 vector add 展示 host/device、`cudaMalloc`/`cudaMemcpy`、`__global__`、kernel launch、全局 index 和边界 guard。
- 可用 15-779 的 block scheduling 图解释资源限制和 occupancy 的直觉，但不必展开完整 occupancy 计算。
- 主要资料：CUDA Programming Guide Part 1.2、2.1、2.3；LCPU Part 1；15-779 slides 5-17、28-43；GPU Puzzles 1-7。

### 1.3 Triton/TileLang: CTA-level Programming

- 从 CUDA elementwise kernel 的机械细节切入：thread index、边界 guard、memory access 都由用户显式描述。
- 并排展示 CUDA、Triton、TileLang 的同一个 elementwise kernel，比较 thread-level 和 program/tile-level 视角。
- Triton 用 `program_id + offsets + mask` 表示一个 program 处理一块数据；TileLang 用 `T.Kernel + T.Parallel` 表示 CTA 内的 tile-level 计算。
- 简单解释 tile abstraction 为什么有用：很多 GPU 优化都围绕“某个 block/CTA 拥有一块数据并在更近的 memory scope 中复用”展开。
- 可以借 15-779 GEMM strawman -> register tiling -> shared-memory tiling 的分析预告这一点，但不要在 Session 1 讲完全部 memory hierarchy 细节。
- 用 TileLang 的最小示例界定 scope：后续会继续看到 `T.copy` 表达数据移动、`T.gemm` 表达矩阵单元计算、`T.Pipelined` 表达流水；本次只要求理解 DSL 把哪些 CUDA 细节封装成了有语义的 primitive。
- 主要资料：Triton Puzzles、TileLang Puzzles、TileLang Language Basics、CUDA Programming Guide Part 2.4、15-779 slides 48-53。

## 准备时建议保留的几个 Takeaway

- GPU 的优势来自 throughput，而不是单线程 latency。
- SIMT 给程序员“每个 thread 独立执行”的视角，但硬件以 warp 为单位共享控制和调度。
- thread/block/grid 反映了执行、通信、同步和资源分配的不同范围，不只是语法层次。
- tile abstraction 来自数据局部性和复用需求；GEMM 的 register/shared-memory tiling 是最直观的例子。
- Triton/TileLang 并非简单缩短 CUDA 代码，而是在选择哪些 mapping、memory movement 和 synchronization 由 compiler 接管，哪些性能关键决策仍由用户表达。
